## 4. HOSTNAME `newQspi` IS A PROPERTY OF `image.ub`, NOT OF A BOARD

The record attributes the hostname `newQspi` to ZCU102 **#1** (the QSPI build).
This is ZCU102 **#2**, booted from a card built today, and it also reports
`newQspi`. The hostname comes from the rootfs inside `image.ub`.

**Consequence: hostname CANNOT be used to distinguish the two ZCU102 boards.**
Any procedure that identifies a board by its prompt is unsafe. This bears on
open decision D-4 (board alignment) — the two boards are now MORE alike, not
less, and neither self-identifies.

## 5. Q4-PRIME — U-BOOT DID NOT CREATE AN ENVIRONMENT FILE

The original Q4 asks whether the FAT redundant environment is initialised on
the board's card. That card is at LPS and Q4 remains open. What was testable
here is the adjacent and arguably more useful question:

**On a fresh FAT32 partition with no environment files, does U-Boot create
them?**

**Measured: NO.** After a full boot to login prompt,
`/run/media/BOOT-mmcblk0p1/` contains exactly the eight files copied. No
`uboot.env`. No `uboot.env.bak`.

**CAVEAT, stated as a caveat:** U-Boot conventionally writes the environment
only on an explicit `saveenv`, not automatically at boot. This result may
therefore be expected behaviour rather than a defect. **NOT MEASURED:** whether
`saveenv` at the U-Boot prompt creates both files on this build. That is a
one-command test at the next power cycle and it decides whether the 2.g
remediation is "run saveenv once during provisioning" or something larger.

## 6. Q1 CONFIRMED ON RUNNING SILICON

Yesterday's answer (`SOW_2G_SEC7_UNKNOWNS.md` Q1) was measured from
`rootfs.cpio` in the build tree. Confirmed live on the booted board:

- `which fw_printenv fw_setenv` -> rc=1, neither present

So the A/B environment mechanism has **neither half** present in practice:
U-Boot is built for a redundant FAT environment, nothing initialises the files,

## 7. CONTROLLER IDENTITY — MEASURED ON HARDWARE

The record states `spidev1.0` maps to AXI Quad SPI at `0xa0000000`, not PS SPI1
at `0xff050000`. That was established by analysis. It is now measured:

```
readlink -f /sys/bus/spi/devices/spi1.0
  -> /sys/devices/platform/axi/a0000000.axi_quad_spi/spi_master/spi1/spi1.0

readlink -f /sys/devices/platform/axi/a0000000.axi_quad_spi/of_node
  -> /sys/firmware/devicetree/base/axi/axi_quad_spi@a0000000

cat /sys/bus/spi/devices/spi1.0/modalias  ->  spi:dh2228fv
```

Two masters exist after the overlay: `spi0` = QSPI `ff0f0000`, `spi1` = AXI
Quad SPI `a0000000`. **PS SPI1 remains unreachable from Linux** — see below.

`MSU2_Session_Recap_Onboarding.docx` presents its bare-metal-vs-Linux table as
same-wire-same-clock. This measurement is direct evidence against that framing
and supports the reconciliation item in `SESSION_RECAP_20260819.md` 7.

## 8. BASE DTB ENABLES ONLY QSPI

Before any overlay, measured from `/proc/device-tree/axi/`:

```
spi@ff040000 (PS SPI0)   status = disabled
spi@ff050000 (PS SPI1)   status = disabled   -- and has NO child nodes at all
spi@ff0f0000 (QSPI)      status = okay
```

`/sys/bus/spi/devices/` was empty; `/sys/class/spi_master/` held only `spi0`.
`fpga0/state` was `unknown`.

**So "image.ub is the spidev-enabled kernel" means the spidev DRIVER is built
in — not that a spidev DEVICE exists.** The device comes entirely from the PL
overlay. A card built from `RE-FLASH.md` alone boots but has no SPI device and
cannot run the benchmark binaries it carries.

One boot-time error, present before any of today's actions and not caused by
them: `spi_master spi0: cannot find modalias for /axi/spi@ff0f0000/flash@0`.
The QSPI controller probes; its flash child does not bind. Recorded, not
investigated.

### The manual bitstream load is REDUNDANT

`dmesg` shows the FPGA programmed **twice**: at t=434 by the explicit `echo`,
and again at t=496 when the overlay was applied. The overlay carries
`/fpga-region/firmware-name`, measured as:

```
cat /proc/device-tree/fpga-region/firmware-name  ->  spi_benchmark_wrapper.bit.bin
```

So applying the overlay programs the PL by itself. README's separate
`fpga_manager/firmware` write is not needed — though the `.bit.bin` must still
be in the firmware search path for the overlay to find it.

This also explains the two overlay warnings (`memory leak will occur if overlay
removed`, on `firmware-name` and `resets`) — they concern overlay REMOVAL and
were not caused by anything done here.

## 10. DOCUMENTATION DEFECTS — found by following the documents

**D1. `scripts/DEPLOY_AND_TEST.md` step 2 omits the bitstream load entirely.**
It copies the `.bit.bin` into `/lib/firmware` and never writes to
`/sys/class/fpga_manager/fpga0/firmware`. `README.md:133` has that line. A
reader following DEPLOY_AND_TEST alone never programs the PL by that route.
(Per section 9 the overlay would program it anyway — but the document does not
say so, so it reads as an omission, not a deliberate simplification.)

**D2. Firmware path disagreement.** `README.md:131-132` uses
`/usr/lib/firmware`; `DEPLOY_AND_TEST.md` uses `/lib/firmware`. Only the README
path was exercised today; `/lib/firmware` was NOT tested and may or may not be
searched on this rootfs.

**D3. Mount-path case disagreement.** README uses `/run/media/BOOT-mmcblk0p1`;
`DEPLOY_AND_TEST.md` uses `/run/media/boot-mmcblk0p1` (lowercase). The measured
mount point is **uppercase `BOOT-`**. The DEPLOY_AND_TEST commands would fail
as written.

**D4. `sd-images/RE-FLASH.md` is incomplete as a bring-up procedure.** It ends
at "set SW6 and power on" and never mentions the bitstream, the overlay, or
that `/dev/spidev*` will not exist without them. It also lacks:
- any `partprobe` after `parted` (the kernel may hold a stale partition table
  and `mkfs` can fail on a missing node — `partprobe` was added today)
- any md5 verification after copying (a truncated 55 MB `image.ub` would
  present as a boot failure, not a copy failure)
- a note that it assumes a 16-32 GB card; this one is 58 GB, which worked

**D5. Nothing cross-references.** `RE-FLASH.md` does not point to
`README.md:130-146` or to `DEPLOY_AND_TEST.md`. Bring-up currently requires
knowing which three documents to read and in which order.

## 11. METHOD ERROR — recorded

`find /proc/device-tree -name '*quad_spi*'` returned nothing, and the node
exists. Cause: `/proc/device-tree` is a **symlink** to
`/sys/firmware/devicetree/base`, and `find` does not traverse symlinks without
`-L`. The probe could not have matched anything. `find -L` returns
`/proc/device-tree/axi/axi_quad_spi@a0000000` correctly.

**Rule: when a probe under `/proc` or `/sys` returns empty, check whether the
path is a symlink before concluding the target is absent.**

This is the third check-that-could-not-have-failed in one day, after
`echo $?`-after-a-pipeline (`SESSION_RECAP_20260819.md` 3.2) and
`objcopy -O binary` on non-SHF_ALLOC sections
(`STEP_0_5_CROSSSITE_20260820.md`). The recurring shape is a probe whose
failure mode is indistinguishable from a true negative. Every such probe needs
a positive control or a structural check before its empty result is believed.
